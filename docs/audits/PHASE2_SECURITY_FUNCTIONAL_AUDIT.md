# Auditoría Fase 2 — seguimiento de hallazgos

## Objetivo
Concentrar los hallazgos reproducibles y las correcciones de seguridad/funcionalidad en una rama y PR independientes. Cada cambio debe validarse antes de fusionarse a `master` y desplegarse a producción.

## Reglas de trabajo
- No modificar producción directamente ni alterar/limpiar la base de datos de pruebas.
- Corregir por bloques pequeños; documentar evidencia, causa, solución y prueba.
- No ejecutar `npm audit fix --force` ni migraciones mayores de framework/estilos sin revisar compatibilidad.
- No marcar como aprobada una verificación omitida. El paso informativo de `npm audit` dentro de `quality` conserva `continue-on-error: true`; el job separado `Dependency security gate` es el control bloqueante y actualmente falla por advisories de producción.
- Fusionar cada bloque validado para no volver a trabajar soluciones ya integradas.

## Contexto del quality gate
El workflow `.github/workflows/quality-gate.yml` ejecuta un job independiente `Dependency security gate` con `npm audit --omit=dev --audit-level=high` sin `continue-on-error`, por lo que bloquea la PR si quedan vulnerabilidades altas/críticas. El paso duplicado dentro de `quality` sigue siendo informativo (`continue-on-error: true`) para que se puedan consultar sus resultados sin impedir que se ejecuten las regresiones. En HEAD `1219c780a1bdbbb965c41a7a8f6ae3d27f2a4895`, el job de seguridad falla por 7 advisories de producción; no debe considerarse resuelto hasta corregir las dependencias y lograr que ese job pase.

Los cambios de infraestructura o de plan de Supabase se registrarán aparte; no se aplicarán sin autorización.
